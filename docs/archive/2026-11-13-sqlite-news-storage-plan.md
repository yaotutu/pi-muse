# 服务端共享 SQLite 与新闻首批接入规划

> 归档说明（2026-11-16 整理分支时归档）：本规划已实现，落地提交见 `feat(storage): migrate business facts to main.sqlite` 系列；当前实现事实以 [sqlite 存储说明](../sqlite-storage.md)、实际 contracts 与 `/docs` 为准。RSS 解析加固随后单独移植合入（原 rss-pipeline WIP），与本存储迁移解耦。

日期：2026-11-13。状态：讨论草案，仅规划；本文件不授权实现、真实数据迁移或共享后端升级。

## 1. 已确认的范围

- 本次只处理服务端。客户端本地存储不改。
- pi-coding-agent 及其管理的聊天历史、执行循环保持原样，暂不纳入 SQLite 改造。
- 我们自有的业务持久数据逐步使用同一份 SQLite；首个模块为内置新闻。
- 服务端代码直接使用数据库，Agent 通过数据库工具操作同一份库。
- Agent 对整库可自主读写、建表、改结构、删表；不设置角色、表白名单或逐次 SQL 审批。
- 以下是协作规范和结构约束，不是 Agent 权限限制。用户允许自主操作，不等于任意 DDL 都不会影响服务端功能，规范不能提供这种保证。
- 不把旧 RSS 优化草稿的坏条目策略、新响应字段等捆绑进此次存储迁移。

## 2. 总体结构

一个服务实例管理一份数据库，暂拟逻辑路径 `DATA_DIR/pi-muse.sqlite`，名称待定。

- 服务端组装层统一创建/关闭连接、管理事务和迁移入口，各模块不各开一份无协调的 writer。
- 优先使用已核查可用的 Node 内置 SQLite；具体 API/版本及耐久参数实施前锁定。不开独立数据库服务，不引入厚重 ORM。
- SQL 放在对应模块的数据访问代码中；业务层保留业务判断，HTTP 契约尽量不变。
- Agent 使用同一数据库连接管理入口，不再单独划工作数据库，也不要求业务代码经过 Agent 工具。
- 不新造万能 document/blob 表、通用业务事件总线或多租户架构。

## 3. 跨功能最小规范

### 3.1 命名与模块

- 表/字段/索引统一 ASCII snake_case。
- 领域表使用模块前缀：本次 `news_`；未来可按实际需求使用 `memory_`、`reminder_`、`journal_`、`health_` 等。
- 公共设施使用 `app_` 前缀，首批只需要迁移账本等确有用途的表。
- 索引和约束名称能读出表及用途。前缀只用于辨认职责，不代表访问隔离。
- 不因将来可能用到健康/提醒就提前建表，也不预加 user_id、tenant_id、ACL 等当前无需求字段。

### 3.2 标识与关系

- 对外业务 ID 保持 TEXT 及现有值，不以 SQLite 自增主键替换文章、来源、评论、run 的身份。
- 联合唯一键表达已有幂等规则；新闻是 `(source_id, external_id)`，不是标题或原文 URL 去重。
- 一对多/多对多用关系表，不把整个集合藏在 JSON 数组里。
- 外键和 CHECK 表达真正的关系与有效状态，不作为 Agent 授权机制。
- 每条关系明确删除语义，不默认级联。历史快照不能错误绑定到必须仍存在的配置记录。

### 3.3 时间与技术字段

- 第一版沿用接口已有的 UTC ISO 8601 文本格式，避免混入 SQLite 默认的空格格式时间或无标识的秒/毫秒整数。
- 业务发生时间和系统接纳/记录时间分开，不强迫所有表具有完全相同的字段。
- 反馈最近触达顺序必须独立保存，不能仅用精度有限的 updated_at 推断原数组顺序。
- 新模块涉及健康数值时值和单位分开；涉及周期提醒时明确时区。这里只约定原则，不预先设计这些业务。
- ID、时间、顺序等技术字段尽量由默认值、明确的数据访问操作或必要的简单触发器维护，使服务端和 Agent 写入能遵守同一约定。哪些触发器值得使用待实施设计，不把业务流程藏进复杂触发器。

### 3.4 查询与事务

- 查询显式选择列，不依赖 SELECT * 后做严格字段解析，避免 Agent 扩列导致现有业务无谓失效。
- 服务端对值参数绑定；分页、排序必须有稳定的同值次序。
- 事务包数据库内相关更新，不跨模型请求、网络抓取或人工等待。
- 唯一约束、外键与短事务负责数据一致性；不另做表级权限系统。
- SQLite 的一个 writer 不等于无需协调。Agent 事务与服务端事务必须由同一入口管理，不能留下跨调用悬空事务污染下一次请求。
- Agent 的 SQL 改动不自动等同于业务动作，例如改一行状态不等于已经执行分析/发出提醒。语义由表说明和业务调用约定解释，不靠权限拦截。

### 3.5 版本与可发现性

- 建立 `app_schema_migrations`，保存版本、名称、校验值、应用时间；正式模块的结构变化以可审查迁移记录维护。
- Agent 可以读写整库；常规协作约定是不伪造迁移账本，探索后长期保留的结构应与后续正式版本核对、登记，不能让下一次升级盲目覆盖或重复建表。
- Agent 可通过 sqlite_schema、PRAGMA 等发现真实表、列和索引；配一份简短的模块含义/状态/写入示例说明，不维护与实际库脱节的巨型元数据系统。
- 不擅自把当前真实 JSON 导入做成启动时隐式动作。真实数据切换另行确认。

## 4. 新闻第一版逻辑表

这是逻辑划分，不是已经确定的完整 DDL。实施前逐字段映射现有 NewsState/InformationState，先保行为不变。

| 表 | 职责 |
| --- | --- |
| news_sources | 当前 RSS 源配置及其抓取健康状态 |
| news_articles | 已接纳文章、来源快照、原始标识、时间、处理状态与当前批次关联 |
| news_article_feedback | 每篇当前 reaction/saved 与最近触达顺序，不是点赞次数或操作流水 |
| news_article_comments | 评论 ID、正文、顺序和创建/更新时间；不以 JSON 数组塞进反馈行 |
| news_analysis_runs | 批次身份、状态、时间、类型、模型成功/失败事实 |
| news_analysis_run_items | 批次与文章的成员关系及原顺序，保留历次批次关系 |
| news_analysis_decisions | 批次中逐篇推荐/静默及理由；不只保存最后一个布尔值 |
| news_state | 新闻模块的少量单例状态、处理设置、反馈顺序计数及 learnedNotes 等自有状态 |

核心约定：

- feedback 中 like/dislike/null 互斥，saved 独立；评论可单独增删。
- 最近最多 20 篇反馈样本仍按最近触达顺序读取，不能因改表排序偷偷改变推荐输入。
- 推荐来自成功批次；点赞/收藏不自动重算既有推荐，不新增模型调用。
- 删除订阅源仍保留旧文章和反馈。`news_articles` 的历史 source_id/source_title 是来源事实快照，不能强加“来源必须仍在 news_sources”且会阻止删源的外键，也不能 ON DELETE CASCADE 把文章删掉。
- 文章的现有 ID、publishedAt/acceptedAt、processing status、runId、顺序、原文链接和来源标题须有明确映射；不能把发布日期当数据库更新时间。
- 明确偏好仍遵循现有 main 指令入口，新闻模块不新增另一份可独立编辑的用户规则。旧 preferences.notes 与指令的冗余/回退关系须在导入预检时核对，发现差异先报告，不自动覆盖、丢弃或合并用户规则。
- 来源中若存在当前逻辑表未覆盖的合法历史事实（例如旧 publications），预检须报告并完善映射，不能为了表方案简洁静默丢数据。

## 5. 不能忽略的现有代码耦合

新闻目前通过 createNewsProcessingRepository 复用 InformationService 的整聚合 read/update，短信也使用同一类接口。

因此第一期不能仅把 news.json 换成一行 JSON blob。需要设计可表达按条目/批次/反馈访问和事务的 repository 方法，复用处理算法，不重新造新闻模型循环。

如果调整共享接口，应同步所有实现和调用方，但不把短信数据迁移偷偷纳入本期。过渡范围、最终接口及去掉整聚合重写的完成标准，在实现前明确。

## 6. 首期保持不变的行为

- RSS 抓取策略、新闻推荐策略、喜欢/不喜欢/收藏语义。
- 反馈不会立刻触发模型，已有推荐不因反馈立即重算。
- Agent 的 SQL 工具无需逐次数据库写入审批；文件 write/edit 的既有版本审批仍属另一能力，不因此改动。
- pi-coding-agent 的历史、revision、执行和取消方式。
- 当前客户端请求/响应结构。存储变化不应顺手加入 skipped/resetDeferred 等未确定的新协议。
- 模型成功、数据库已提交、通知/其他副作用完成，仍须区分，SQLite 不自动回滚外部副作用。

## 7. 实施分步（待批准）

1. 确认上述约定、第一批表和历史映射；盘点新闻读写入口及当前查询排序。
2. 建最薄的共享 SQLite 连接、事务、迁移和备份能力，并用隔离合成数据验证。
3. 新闻关系化存储与查询接入，补来源删除、反馈/评论、批次与推荐回归；不改变业务行为。
4. 数据库工具接入同一实例。工具可执行任意 SQL，按查询/执行/事务返回清晰结果；返回内容大小和分页是交互呈现问题，不暗中修改 SQL 或隐藏权限规则。
5. 做独立导入预检/转换工具。先在合成数据和授权副本验证 ID、数量、关系、顺序、空值和状态，再提出真实切换步骤。
6. 真实切换另行确认，切换前收敛写入、备份、导入、完整性核对；不长期 JSON/SQLite 双写。旧源文件只作为备份保留，不自动删除。

后续模块逐个遵循同一命名、ID、时间、关系、迁移约定接入。等真实出现跨模块需求，再增加有明确归属的公共表，不提前造万能生活事件/实体模型。
