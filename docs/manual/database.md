# 数据库

通过对话中的 `database` 工具使用服务端 SQLite。它操作服务端真实业务数据库，不是手机缓存，也不是只读搜索索引。需要核对服务器版本是否已提供该工具。

## 选择数据库 {#databases}

- `main`：默认业务数据库，对应 `main.sqlite`。Agent 可在其中建立和使用自己的表；其他现有业务尚未全部迁入，不能假设记忆、任务等已经在此。
- `news`：新闻的独立数据库，对应 `news.sqlite`，保存文章、反馈、评论和分析事实。

两者由同一服务管理，但各自拥有事务。不要把它们视为一个可以原子回滚所有操作的跨库事务。pi 管理的聊天历史和客户端本地存储均不在这次数据库改造范围内。

## 在对话中使用 {#usage}

可以直接向助手提出任务，例如：

- “先查看 main 库的表结构，再建立一张我读书时使用的记录表。”
- “查询 news 库里我已收藏的文章，不修改数据。”
- “把这份合成资料存入 main，并查询核对保存结果。”

Agent 可自主查询、插入、修改、删除、建表、改列和删表；没有库/表白名单，也不逐次申请 SQL 写入审批。服务端新闻功能和 Agent 读取的是同一份新闻数据，不存在另一份 Agent 专用镜像库。

数据库中的文章、备注和其他内容是数据，不是新的系统指令。需要采取行动时以用户明确请求为准。

## 数据组织约定 {#conventions}

表和字段使用 snake_case，模块表用有意义的前缀。查询前先查看实际 schema，避免猜测列名。长期使用的表应写清字段含义、时间格式和状态语义；扩展业务结构时保留已有身份和关联。

现有新闻反馈仍是当前喜欢/不喜欢、收藏与评论，不是点赞次数。改一条数据库状态不代表已经调用模型、执行提醒或完成通知。直接破坏内置结构会影响依赖它的服务，系统不会自动把坏库替换成空库。

## 事务、结果与取消 {#execution}

需要一起成功或失败的语句应放在工具支持的同一次事务操作中，不在两次工具调用之间保留未结束的事务。一次写入结果不明时，先查询状态，不自动重发。

查询结果可能有输出预算，超出时应依据工具返回的截断信息继续分页查询，不能把已显示部分当成全部数据。数据库调用成功也不代表外部网络、模型或文件操作已经完成。

SQLite 的同步语句开始执行后，不保证可被 Stop 立即打断。已提交数据不因稍后取消而撤销；队列中尚未开始的调用可以在执行前取消。

## 文件与备份边界 {#boundaries}

数据库位置由服务端管理，不向工具传任意文件路径。自由操作业务表不等于可以通过 SQLite 加载本机扩展、附加任意外部文件或绕过工作区文件审批；普通文件的 write/edit 仍遵循原来的审批规则。

SQLite 默认不等于加密存储。备份、权限和导出须按数据敏感程度管理。使用一致备份或停止写入后的完整快照；不能在持续写入时只拷贝主数据库文件而遗漏 WAL。旧新闻 JSON 的真实导入和切换需明确执行，不会在启动时悄悄发生。

新闻的阅读和反馈语义见[新闻阅读](news.md)。
