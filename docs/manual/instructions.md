# 指令与提示词

Pi Muse 使用统一的三层结构组装模型上下文：服务端内置系统提示词保持稳定行为与安全边界，用户指令与人设文档提供最高优先级的个性定制，当次输入提供当前上下文或待处理数据。本文按当前服务端源码整理；移动客户端实际界面以你安装的 Release 为准。

## 三层提示词结构 {#three-layers}

每次向模型发起请求时，服务端按以下三层拼装上下文：

1. **系统提示词（只读，随源码发布）**：统一托管在服务端仓库 `prompts/` 目录，使用英文模板以提升结构化工具调用与跨场景稳定性，并默认要求面向中文体验返回简体中文内容（当你在指令中明确指定其他语言时以你的指令为准）。服务端运行期间实时读取仓库模板（构建模式下使用随构建同步的产物），**不支持**通过数据目录覆盖系统提示词。
2. **用户指令与已归纳行为习惯**：由你在工作区持久化维护的 Markdown 文档（具有最高用户权限），以及短信后台领域由通用习惯引擎定期沉淀（或你手动管理）的结构化行为习惯列表。
3. **当次待处理输入**：普通聊天中为用户输入、历史与按需检索到的长期记忆；短信后台整理轮中为尚未消化的近期反馈热缓冲样本，以及显式包裹在 `UNTRUSTED INPUT DATA` 边界内的原始内容，防止外部内容提示词注入。

## 四份工作区托管文档 {#managed-files}

全部持久化人设与用户指令均保存在唯一工作区 `DATA_DIR/workspace/` 下，共四份托管 Markdown 文件：

| 文档路径（相对 `workspace/`） | 作用范围 | 主要编辑入口 | 生效时机与上限 |
| --- | --- | --- | --- |
| `assistant/AGENTS.md` | 所有聊天会话共享的助手指令 | 设置 → 助手指令；工作区文件；聊天中的 `instructions` 工具（需审批） | 下一轮聊天起生效；单文件保存上限 20,000 字符；空串清空 |
| `assistant/SOUL.md` | 助手性格、表达风格与人设定位 | 设置 → 身份与人设；工作区文件；模型 `write` / `edit`（需审批） | 下一轮聊天起全局生效；单文件保存上限 20,000 字符；空串清空 |
| `assistant/USER.md` | 你的个人背景、称呼与长期偏好 | 设置 → 身份与人设；工作区文件；模型 `write` / `edit`（需审批） | 下一轮聊天起全局生效；单文件保存上限 20,000 字符；空串清空 |
| `subagents/sms/AGENTS.md` | 短信/信息后台过滤与通知判断规则 | 设置 → 短信偏好；工作区文件；聊天中的 `subagent`（需审批） | 下一次短信分析批次起生效；单文件保存上限 20,000 字符 |

这四份文件均采用**最后一次成功保存生效**。短信后台不会读取聊天技能、`assistant/AGENTS.md` 或全局 `memory.md`；主对话也通过统一的 `subagent` 工具按需协同读写对应子代理指令。

全新实例首次初始化工作区时，还会额外生成一份一次性的 `workspace/assistant/BOOTSTRAP.md` 破冰引导（仅在 `SOUL.md` 与 `USER.md` 均为空时注入主聊天，引导你用 1～2 轮对话自然设定助手风格与个人称呼）。一旦你在聊天中审批写入或通过设置页保存了 `SOUL.md` / `USER.md`（或手动删除 `BOOTSTRAP.md`），该引导自动退场，之后重启也不会再次生成。

## 用顶部 Frontmatter 拆分引用 {#frontmatter-include}

当某个指令或人设文件变长时，无需把所有规则堆在同一份 Markdown 中。上述**全部四份**工作区托管文档都支持在**文件最顶部**使用标准 YAML Frontmatter `include:` 引用其他纯文本文件。

```markdown
---
include:
  - ./bank.md
  - ./快递规则.md
  - ../../files/vip-contacts.md
---

其余短信均按默认静默规则处理。
```

同时支持单条字符串写法与行内数组写法：

```markdown
---
include: ./bank.md
---
```

```markdown
---
include: [./bank.md, ./快递规则.md]
---
```

### 引用规则与边界 {#include-rules}

- **仅识别文件最顶部**：只有放在文件最开头的 YAML Frontmatter 且显式包含 `include` 键时才会展开。正文中间的 `---` 分隔线、不含 `include` 的普通 Frontmatter（例如仅有 `title:`）或语法损坏的 YAML 会原样保留、不做展开。
- **相对路径基准**：每条路径都**相对于当前文件所在目录**解析，支持 UTF-8 文件名（如 `./快递规则.md`）；需要跨助手与后台领域复用清单（例如共享 `files/vip-contacts.md`）时，可使用相对路径向上到达 `workspace/` 内其他子目录。
- **支持范围与严格禁区**：四份托管文档本身及被其引用的子文件均可继续使用 `include:`；系统或手动维护的行为习惯条文与原始短信内容**绝不解析** `include:`，防止模型或外部输入反向读取工作区其他文件。
- **工作区安全限制**：引用目标必须位于唯一工作区 `workspace/` 内，且必须是有效的 UTF-8 纯文本普通文件（不含 NUL 字节）。绝对路径、反斜杠、跳出 `workspace/` 的 `..`、符号链接、目录与二进制文件一律被拒绝并跳过。
- **嵌套、环路与字符上限**：支持最多 `5` 层递归引用；同一次解析中遇到自环、互环或菱形重复引用时自动去重并只保留首次展开；整份展开结果（含所有已引入内容）上限为 `60,000` 字符，超出后保留正文与已展开部分并在末尾附加截断注释 `<!-- include truncated: resolved character limit reached -->`。
- **展开标记**：每个非空子文件会以 `<!-- begin include: <workspace相对路径> -->` 与 `<!-- end include: <workspace相对路径> -->` 包裹，方便模型清楚规则来源与所在文件。

### 存盘与展开行为 {#include-storage-behavior}

- **读写始终保持原文并附带诊断**：HTTP 接口（`/api/assistant/instructions`、`/api/profile`、`/api/information/preferences`）、工作区文件编辑器以及助手读取工具均返回并保存含顶部 `include:` 的原始 Markdown，绝不会把展开内容拍平写回主文件。其中 `/api/assistant/instructions` 与 `/api/information/preferences` 会额外返回 `includes` 诊断数组，逐项说明每个引用的状态（`loaded`、`missing`、`invalid`、`cycle`、`depth_exceeded`、`truncated`、`empty`）及工作区相对路径。
- **注入模型前实时展开**：每次聊天轮、短信判定及 Dream 查重都会重新读取并展开所有引用文件；修改任意被引入的子文件后，从下一轮模型调用起立即生效，不需要重新保存主文件。
- **缺失或非法引用静默跳过**：被引用的文件尚未创建、已删除、越界或不是纯文本时，服务端仅记入 `includes` 诊断状态并在组装提示词时跳过该条目、保留其余有效规则，不会阻止保存或中断执行。
- **与 Dream 协作**：Dream 整理记忆时会读取展开后的完整文档用于查重对比；你在确认待决建议并应用到 `USER.md`、`SOUL.md` 或 `AGENTS.md` 时，写回过程基于原始文本在末尾去重追加，不会破坏文件顶部的 `include:` 块。

## 短信领域规则 {#sms-domains}

### 短信默认静默与四级优先级 {#sms-precedence}

短信助手默认关闭，开启手机短信同步或收到短信上传时会自动开启。系统提示词采用**默认静默（Default-Silent）**基线——拿不准且无明确指令时默认判为 `silent`（如促销广告、运营商营销、常规已完成登录验证码、无须操作的普通物流中转），仅在确认值得打扰时发出提醒（如取件码/驿站/配送异常、大额或异常账单、账号安全告警、行程变更等）。模型判定按以下顺序生效：

1. **你的明确指令**：`workspace/subagents/sms/AGENTS.md`（最高权威）。
2. **近期未消化反馈**：你在主聊天中对近期短信通知留下的喜欢、不喜欢、收藏与评论纠偏（作为热缓冲实时传入，直到下一次习惯归纳完成）。
3. **已归纳行为习惯**：通用习惯引擎按消费游标每 2 小时或每累积 5 条去重反馈后沉淀（及你手动编辑）的长期行为规则，保存在 `main.sqlite`，不会丢失早期偏好。
4. **默认静默基线**：前三层均未明确覆盖时的保守过滤兜底。

短信后台严格区分日常实时队列（`realtime`，重要结果直接写入 `main` 聊天通知，全静默时不发消息）与历史批量归档队列（`archive`，独立导入后逐批增量向习惯库沉淀规则，清空后至多生成 1 条不超过 1,200 字的中文总览简报）。个别短信被大模型内容安全审核拒绝时会自动被单独隔离，不再拖垮同批其他短信；归档简报仍会发出并自然告知被跳过的条数。

## 编辑方式与安全边界 {#editing-and-boundaries}

1. **设置页编辑**：在移动端「设置」中对应入口直接修改保存；修改拆分出来的子文件可在[附件、文件与审批](files-and-approvals.md#manage-workspace-files)中的「工作区文件」完成（先查看修改前后完整预览再确认）。
2. **聊天协作编辑**：在主聊天中要求助手更新助手指令或短信规则，助手通过 `instructions` 或 `subagent` 工具提出修改建议。

::: warning 安全与隐私边界
- 所有指令、人设、技能开关及 `include:` 展开内容均不能为模型增加工具、放宽 `workspace/` 路径边界或跳过 `write` / `edit` 人工审批（详见[附件、文件与审批](files-and-approvals.md)）。
- 生效后的指令与人设文本会发送给服务端配置的外部模型服务，请勿在其中存放密码、模型 API Key、AccessKey 或敏感凭据。
:::

## 排错 {#troubleshooting}

| 现象 | 检查项 | 处理方式 |
| --- | --- | --- |
| 修改子文件后主文件接口未显示变化 | 正常行为 | 读取与编辑接口保持原文；发一条新对话或触发下一轮筛选验证模型行为是否已生效 |
| 顶部的 `include:` 被原样发给模型未展开 | 是否位于文件最顶部、是否使用合法 YAML、键名是否为 `include` | 确认 `---` 前没有任何空行或正文文本，键名拼写为 `include` 且语法完整 |
| 引用的某个文件没有进入模型上下文 | 文件是否存在、是否在 `workspace/` 内、是否含符号链接、嵌套是否超过 5 层、文件是否为纯 UTF-8 文本 | 在「工作区文件」确认路径相对当前目录正确且为非空纯文本普通文件 |
| 出现截断注释 `resolved character limit reached` | 展开总字数是否超过 `60,000` 字符 | 精简冗余说明或拆分无须长期注入的资料到按需查阅的文件中 |
| 新建或修改引用路径写不进去 | 工作区手动新建文件界面路径校验规则 | 手动新建子文件时，若客户端界面要求 ASCII 路径名请用英文文件名；已存在的 UTF-8 文件名可直接被 `include:` 引用 |
