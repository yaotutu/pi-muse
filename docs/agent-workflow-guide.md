# 开发 Agent 工作方式

本文面向在 Pi Muse 仓库工作的开发 Agent（当前主力为 Antigravity，兼容 Claude Code）。它约束开发过程，不是产品 Agent 的系统提示词，不改变 pi SDK、业务模型或实例规则。各目录 `AGENTS.md` 统一维护开发命令、高层架构与项目约束（Antigravity 自动加载 `AGENTS.md` 与 `.agents/skills.json`，Claude Code 通过同目录 `CLAUDE.md` 的 `@AGENTS.md` 加载同一份规则）；架构、测试和文档分别由专项指南维护。

## 任务与执行（积极委派）

> **当前协作模式（2026-11-22 起）**：Pi Muse 是**一核多端（Server-First + 多形态接入端）**项目，外部接入端涵盖手机 App、Web、ESP32/单片机、智能音箱、Webhook、脚本等。本工作区服务端开发 Agent 虽能只读查看全部代码以保持全局视角，但**只负责服务端 `pi-muse-server/`（含自有 `web/` 联调台），其他项目及非服务端文件一概不管**（不修改、不代为清理、不越界干预）。平时正常开发服务端并同步 `/docs` 与 `/openapi.json`；**仅当本次改动存在需要外部接入端注意的事项时**，顺手记入[服务端接入须知与变更记录](client-notes.md)（通用协作范式变化同步[客户端接入与协作指南](client-integration-guide.md)），供各类接入端 Agent 按需自读并自主实现；若对其他项目有建议或发现其他项目某些文件已旧/无用，只需在工作区根目录 `client-requests.md` 给对应项目留一条 `NOTE-*` 留言即可，无需再管；反向地，接入端可在工作区根目录 `client-requests.md` 追加 `REQ-*` 诉求，服务端 Agent 评审并在原条目回写状态与 `/docs` 落地入口，具有普适性的外部影响再同步[服务端接入须知与变更记录](client-notes.md)。除非用户明确重新授权跨端写代码，否则不得修改客户端文件。

用户已于 2026-11-05 授权积极委派。主会话负责需求理解、产品/架构/契约/安全决策、派单、diff 审查、真实验收、契约与文档同步及本地提交；调查与实现优先交给执行者。委派不是强制的：小改动、快速查找、需要全局上下文的判断由主会话直接完成，不为委派而委派。

任务开始时确定目标、写集、非目标和验收，不为每次小修改创建任务文档。跨端任务先确定契约及失败语义，再修改对应调用方。根目录不属于 Git，两端提交分别检查；未提交文件不等于可覆盖的文件。

未实施方案留在 backlog，不能因为被记录就开始开发。历史分工、分支、端口、PID、测试数量与安装版本都是线索；重新核对当前仓库和进程，不把旧报告或记忆当成现状。涉及安全或授权且无法从当前请求判断时再询问用户。

## 分支与工作目录

两端各自的 `main` 是唯一当前开发基线。临时任务分支/worktree 用于隔离未完成写集，验收后在同一任务中合回 main 并删除，不把已完成工作长期留在旧分支，也不保留可运行的新旧双轨。

创建执行者 worktree 后先核对其 HEAD 与本次确认的 main 基线，不假设工具默认选择了最新本地提交。基线不符时先由主会话处理，再派单实现；跨端各核对自己的仓库，不在根目录运行 Git。

删除分支前确认提交已成为 main 的祖先；移除 worktree 前确认无独有改动，执行者未提交补丁需审查、整合并逐文件核对一致。不以强制清理掩盖未合并改动。保留 Git 历史、验收证据及发布标签；开发实例数据可按任务清理，不擅自删除远端分支或 push。

## 开发执行者与委派边界

| 执行者 | 当前状态 | 适用与边界 |
| --- | --- | --- |
| Antigravity（主会话与原生 subagent） | ✅ 当前主力，同时保留 Claude Code 兼容 | 需求理解、决策、派单、diff 审查、真实验收与本地提交；原生 `read_file` 支持看图，原生 `invoke_subagent`（`research` / `self` / `image-generator`）支持子 Agent 委派，可通过 `Workspace: "share"` 或 git worktree 隔离写集 |
| Claude Code（主会话与原生 sub agent） | ✅ 兼容可用，经同目录 `CLAUDE.md`（`@AGENTS.md`）共享同一套规则 | 需求理解、决策、派单、diff 审查、真实验收与本地提交；sub agent 默认继承当前会话模型 |

- 不再为子任务指定第三方模型或维护多模型路由表；主会话与原生子 Agent 直接使用当前会话默认模型。
- 执行者不递归委派；并行任务用独立 worktree/分支隔离写集；执行者不做 commit、push、发布或修改版本，产物以工作区改动交回，主会话审查后统一提交。
- 外部工具或子代理可按任务使用本项目开发数据，不为此强制创建隔离目录；凭据和密钥仍只由必要的配置入口读取，不在派单中附带秘密。执行失败、限流或超时如实记录，不自动换模型重放。

## 开发 Agent 工具与上下文

- 文件读取/修改优先使用当前会话提供的专用工具，搜索、构建和 Git 使用可用工具；不要在项目规则里硬编码另一执行器的命令格式或内部工具协议。
- 优先读取当前模块源码、测试和契约，按任务加载指南；archive、截图目录、发布流水不默认整包加载。需要用户看图时用正文内嵌实际存在的图片，不只给路径。
- 使用本会话实际可用的浏览器、设备和视觉能力；工具缺失时如实报告，不沿用旧模型“无多模态”的永久假设，也不把未查看的截图描述成已视觉确认。
- 模型和工具由本会话环境提供，不自行切换模型、探测额度、改全局配置或用外部执行器绕过权限/限流。开发工具身份不决定产品业务模型。
- `.agents/`、`.claude/settings*.json`、MCP 配置与用户级配置不是普通文档。不要为“适配 Agent”扩大权限或整体读取可能含凭据的文件；确需配置更改时使用相应配置入口并确认影响。

## 授权与失败

本工作区只有可丢弃的开发环境，不把本地 `.pi-muse/` 或数据库当生产数据保护。用户已授权为开发和验收直接写入、污染、重置、清空或迁移开发业务数据，随时启动、停止、构建和重启本项目服务，无需额外确认。默认直接使用当前后端（通常 12330）与主工程 App，不为保护连续性另造测试包、备用端口或第二套后端。

进程操作只需确认属于本项目并精确限定目标；改动后运行当前代码，启动后核对 health/版本/接口，默认结束时保持本地开发后端可用（涉及 `web/` 联调时按需启动）。已有自动化脚本内建临时实例可继续使用，但不构成人工联调必须隔离的规则。不要为了规则改名、移动或删除与任务无关的文件。

凭据不得泄露，产品审批/权限边界、push、发布、版本写入、CI、正式签名、全局配置与生产/非本项目资源的授权不因此扩大。真实模型费用与已验收模块本地 commit 继续按长期授权执行。

区分工具调用失败、业务执行失败与验收失败。模型限流、503 或工具不可用如实记录，不自动换模型或反复重放。写入结果未明先检查 diff/服务端状态，不直接重复提交。读取可安全重试时也不要形成无边界循环。

不整体输出环境变量、配置或日志；只查看定位所需的非敏感状态。真实 Key、token、用户会话与实例数据不进入报告或仓库，错误证据先脱敏。

## 验证与交付

| 变更 | 验证 |
| --- | --- |
| 服务端代码 | 对应回归与 `pnpm check`，按范围补真实模型、协议和 `web/` 页面验证 |
| 服务端新业务功能 | 本地当前真实后端、外部真实模型、实际浏览器渲染 `/docs` 与 `/openapi.json` 语义核对（涉及工具展示/审批时覆盖 `web/` DEV），有外部注意点顺手记入 [client-notes.md](client-notes.md)（范式变化同步 [client-integration-guide.md](client-integration-guide.md)） |
| 客户端代码（仅在用户重新授权时） | 按对应客户端仓库规则执行 lint/typecheck/test 与相关原生链路 |
| 工程文档或规则 | 差异、引用、路径、命令与规则一致性；不启动业务或模型 |
| 用户手册/文档站 | 按[文档指南](agent-documentation-guide.md)做中英文同步、构建和适用浏览器检查 |

每次发生业务逻辑或功能变更时，必须在同一任务内同步更新受影响的工程文档、成对中英文用户手册（含 `pnpm docs:build`）、契约与必要的 `docs/client-notes.md` 并清理失效旧说明，方可宣布完成；若确无文档影响须在交付中明确说明原因。每次开发完服务端新功能后，主会话必须主动配合本地当前真实后端、外部真实模型以及实际浏览器中的 `/docs` 与 `/openapi.json` 跑完全部服务端验收用例（涉及工具展示/审批时同步验证自有 `web/` DEV）才算完成，不得跑完单测/本地门禁就停下交差；仅当存在无法自行消除的客观环境阻塞时才如实报告阻塞并标“实现待验收”。各类接入端（手机 App、Web、ESP32/音箱、Webhook 等）的端侧实现与验收交由对应接入端自行负责（若用户明确重新授权跨端改动，再按对应仓库规则补齐）。现有默认自动化含模拟模型/fixture，报告时写清本地门禁与真实验收的区别；通过数量不代表全部链路。文档整理不冒充业务复验，历史成功不替代本轮结果。

交付只需说明改了什么、运行了哪些检查、失败/未验项、对外契约与事件变动摘要（含是否在[服务端接入须知与变更记录](client-notes.md)追加条目或更新[客户端接入与协作指南](client-integration-guide.md)，供各类接入端 Agent 参考）以及本地提交。收尾前审查工作区和暂存区 diff，只提交本次模块；不自动 push。根目录文件未被子仓库跟踪时明确说明，不宣称已版本化。

## 派单模板

委派实现类任务时，任务书至少包含以下字段（小任务可在同一段落紧凑表达），并传递当前开发环境、真实模型要求与操作范围；不附加强制隔离或保护开发数据的旧限制：

```text
目标：用户可观察的变化
范围/所有权：允许修改的文件/模块、worktree 位置
非目标：本次明确不做的事
依据/依赖：契约、必读文档、已确定设计
约束：权限、数据、进程、发布、不可自动重试等边界
验收：可观察行为、异常与迟到场景、验证命令
交付：修改位置、实际验证结果、风险与未验证项
```

执行者交付后，主会话独立审查关键实现与实际命令结果，再执行真实验收；不以执行者结论代替验收。
