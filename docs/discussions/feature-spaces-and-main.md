# 功能模块、独立 Space 与交互承接空间的关系

确认日期：2026-11-02。

**状态：已获用户授权，跨端实现与本批集成验收完成。** 本文保存产品关系和边界，具体实现以架构与契约为准；范围、证据和限制见[REQ-014 验收记录](../archive/req-014-feature-spaces.md)。本任务不授权迁移真实数据。当前实现见[架构规范](../architecture.md)，需求索引见[需求池](../backlog.md)。

## 核心结论

新闻、短信处理等在产品上是功能模块（Feature，后文简称功能），底层仍使用各自独立的 Space 保存数据和规则；它们没有独立的用户会话，用户消息交互由指定的工作空间承接。**Feature 默认绑定始终存在的 main Space，但不是永久写死在 main：后续允许用户显式更换交互承接空间。绑定的是 Space，不是某个固定 sessionId，也不会跟随客户端当前选中的空间自动变化。**

“功能自身的数据归属”与“消息交给哪个空间承接”是两件事。本文用“交互承接空间”描述后者，避免“切换归属”被误解为迁移 Feature Space。本次以功能详情页提供显式改绑；目标只能是已建立的普通空间。

本文的“没有独立会话”指没有供用户切换、聊天的专属会话窗口；不要求删除底层执行所需的 pi session 或后台执行上下文。

| 概念 | 职责 | 不意味着什么 |
| --- | --- | --- |
| main Space | 稳定存在的主空间，是 Feature 默认的交互承接空间；当前源码对应 `local-main` | 不是不可更换的唯一目标，也不是所有功能数据的共同存储目录 |
| 交互承接空间 | 为某个 Feature 接收消息、承接讨论和转交反馈的工作空间，默认 main，可显式更换 | 不拥有 Feature 的全部内部数据，不等于客户端当前选中的空间 |
| 承接空间的会话 | 所绑定 Space 当前的聊天载体，会话 ID 可以更换 | 更换会话不等于解除 Feature 与该 Space 的绑定 |
| 普通工作空间 | 用户可切换进入、聊天和处理任务的其他空间，可被指定为功能的承接空间 | 仅仅选中它，不会自动改变 Feature 的绑定 |
| Feature | 新闻、短信等专门能力，按业务选择阅读页面或后台处理形态 | 不要求每个 Feature 都有聊天窗口或底部导航项 |
| Feature Space | 功能自身的数据、配置、偏好和处理记录的归属边界 | 不是普通聊天空间的另一种展示皮肤，也不随交互承接空间切换而迁移数据 |

```text
新闻 Feature -> 新闻 Space：文章、订阅、偏好、处理记录
     |
     +-- 阅读页面 -> 需要讨论时 -> 已绑定承接空间的会话（默认 main）

短信 Feature -> 短信 Space：原始信息、规则、处理记录
     |
     +-- 后台处理 -> 带来源的消息 -> 已绑定承接空间的会话（默认 main）

承接会话中的用户反馈 -> 根据消息来源找到对应 Feature -> 处理其自身数据或偏好
```

## 已确认的功能形态

### 新闻

- 保留新闻专属阅读区域，用于文章列表、阅读、评论等业务交互；阅读界面不是一个独立聊天窗口。
- RSS 是新闻的数据来源与配置，不是另一个与新闻平行的聊天空间。
- 新闻数据与功能配置由新闻自己的 Space 承载；不因为用户切换工作空间而复制一套订阅配置。
- 需要深入讨论时，将选中的新闻及必要来源带到已绑定的交互承接空间，默认 main，而不是自动带到当前选中的其他工作空间。
- 阅读行为不要求逐条产生聊天消息；主动推送的触发条件与频率尚未确定，不能将“统一通信经承接会话”理解成“所有文章都推送到聊天”。

### 短信与消息处理

- 使用自身独立的 Feature Space 保存原始信息、处理偏好和记录。
- 后台完成处理，需要告诉用户的结果走已绑定承接空间的消息通道，默认 main，并标明自己的来源。
- 不另设短信聊天窗口，也不要求专属的日常消息展示区域；必要的设置或管理页面不等于独立聊天入口。
- 用户在承接会话中表达“这类短信不感兴趣”等反馈时，承接方能把该交互带回短信 Feature，而不是只在会话中口头应答。

## 消息来源与反馈回流

1. Feature 处理自己的内容，确定需要传达给用户的结果。
2. 以该 Feature 已绑定的交互承接 Space 为目标（默认 main），由目标空间的会话生命周期解析可承接消息的会话；不能永久绑定创建功能时的 sessionId，也不能在各功能中硬编码 main。
3. 消息携带可验证的功能来源和原始内容关联，用户能看懂来源，承接方也能找到对应 Feature Space 和业务对象。不能只把来源拼成正文，再靠模型猜测归属。
4. 用户针对该消息提出反馈或后续要求时，承接方按关联调用对应功能，功能处理结果由对应交互链路承接。

来源需要表达“哪个功能、针对哪条内容、回到哪里处理”；这是语义要求，不在本文另造 HTTP/SSE 字段规范。具体字段、存储和工具契约统一以当前服务端源码为准，不能由两端各自猜测。

“降低这类短信的提醒频率”应作用于短信功能，“少推荐这类新闻”应作用于新闻功能，不能默认写进承接空间的通用指令或全局用户画像。反馈对象或范围不明确时先澄清，不猜着改规则；也不把一次不喜欢自动等价为永久屏蔽。

承接空间更换会话不解除 Feature 绑定；后续新消息仍以该 Space 为目标。对于仍然保留、可访问的旧消息，其来源关联不应依赖该空间当前的 sessionId。**这不承诺 reset 后保留已清除的聊天或反馈，也不授权恢复旧消息。** 在途发布跨 reset 的取消、拒绝与后续投递边界须在实施时明确，不为实现该关系绕过现有取消保护或自动重放未明写入。

## 显式更换交互承接空间

- 默认由 main 承接，后续可按 Feature 显式改为另一个工作空间；例如新闻改由“研究”空间承接，短信仍由 main 承接。一个功能指定一个承接空间，不扩展成多目标订阅系统。
- 更换只改变后续消息与新发起讨论的落点，不迁移功能数据、不复制功能配置，也不自动搬运历史聊天。
- 已保留消息仍保留原 Feature 来源，不能因更换承接空间而改写为另一功能的数据。旧消息沿其原有来源回流反馈；改绑只影响新接纳的轮次和讨论，在途交互保留旧目标。绑定目标禁止删除，必须先显式改绑；不擅自回退 main 或重发未明消息。

## 所有权与权限

- 功能原始数据、配置和处理事实归对应 Feature Space；承接空间保存实际承接的消息与对话，不复制各功能的完整内部历史。
- 承接空间通过明确的 Feature 能力查询内容、传递反馈；项目内部空间默认互信，可通过下述空间通信向其他空间请求处理，不增加调用白名单或绑定授权。执行时仍使用处理空间的文件工具根，保留符号链接防逃逸、鉴权与模型文件修改审批。
- 业务偏好的结构化管理与模型文件修改需要区分；模型修改文件仍须完整差异、人工审批和版本绑定，不能以“承接空间帮功能改规则”为由绕过。
- 外部新闻与短信原文均是不可信内容；标记功能来源不等于把原文提升成系统指令。
- 本次不迁移、不清理真实数据，不引入通用消息总线、可靠投递队列、自动重试或第二套聊天历史。

## 导航与设置

- 底部保留聊天、新闻、空间；「空间」独立全屏页面管理当前普通空间的文件、规则、技能和维护，二级页隐藏底栏。文件默认原文编辑，不渲染 Markdown；信息归标题副文与信息菜单，不再堆在正文。
- 侧栏单一「设置」入口中的「功能」分组汇总新闻与短信，详情中查看/更换承接空间；新闻继续进入 RSS 来源与新闻偏好，短信进入处理、采集授权与偏好。设置按功能归属而不是按当前聊天重复。
- 新闻、短信与连接、主题、全局资料统一收进「设置」页；侧栏不并列展开功能入口，短信也不混入普通空间设置。
- 虚拟形象交互保留，头像面板继续提供动态、审批与执行历史；它不是 Feature 设置或工作区文件的入口。
- 后台消息通过现有通知流触发所属会话回读，显示结构化来源，不新增另一条 SSE 或系统推送通道。

## 实施与数据边界

- `local-main` 仍是 main 的稳定身份，不重命名真实目录；新闻延续原 `news-internal` 数据，短信初始化独立 `sms-internal`。
- 既有普通空间 information 数据与配置不移动、不删除、不隐式接管；旧的通用 API 保持原所有权语义，而不是新旧两套短信 UI。
- 来源与反馈采用受限 `feature` 能力；工具只能沿当前聊天消息中服务端验证的关联访问原文或保存明确反馈，不获得整个内部空间权限。
- 绑定与消息关系只存必要关联，不复制聊天、原始信息或气泡反馈；reset 清理聊天关联与反馈，保留功能自身条目与偏好。
- 本批真实后端、外部模型、当前 `/docs` 与 Android 原生验收已完成，证据与未验范围见验收记录。后续主动新闻推送、进程终止后的短信接收、多目标订阅不在本次范围。

## 空间双向通信的后续定案

本节是用户后续确认的新决策，优先于上文将交互仅限定为承接空间读取原文/保存反馈的描述。实施状态见需求池 REQ-016，不把本节当作已验收功能。

- 项目内部空间默认互信，不维护调用白名单、绑定授权或逐次确认；main 不是唯一中转站，普通空间与 Feature 空间都可发起和接收请求。凭据、路径安全、模型文件修改审批等既有项目底线不变。
- 区分请求、回复与主动通知。请求交给目标空间执行，回复沿原调用返回；主动通知才采用功能的默认投递目标。修改通知绑定不能改变已发起请求的回复去向，也不改变空间间是否可通信。
- 目标空间在自己的讨论上下文中使用数据、规则和工具；来源只传本次请求与必要背景，不自动复制主聊天历史。按事项保留独立讨论，后续追问沿 discussionId 继续，不把所有短信任务混进一个大会话。
- 一次回复可以是澄清问题；先结束本次执行，向用户展示，再把用户的补充送回同一讨论，不让两个模型替用户作答或互相等待。不硬编码单层委派权限；仅对同一讨论的并发执行返回 busy，防止同一 pi 历史同时追加。
- 第一个实现批次只做通信底座与现有聊天工具入口；卡片上的「继续处理」、独立讨论二级页和明确的输入目标提示属于后续 UI。已有评论是反馈，不因新方案自动变成执行指令。
- 取消按请求传播；来源或目标 reset/delete 先停止关联执行，目标重置清理其讨论。来源重置不擅自删除另一空间已经保存的讨论，但不向来源新会话投递旧回复。不自动恢复崩溃任务、不自动重试未明写入。

后续讨论在本文维护关系与边界；已实现事实仍归架构规范和契约源码，不另建一套影子 API 文档。
